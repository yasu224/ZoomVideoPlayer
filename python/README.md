# Zoom Video Player (Python 版)

`../index.html`（ブラウザ版）を Python で作り直したものです。
画面は PySide6 (Qt)、デコードは PyAV (FFmpeg) を使うので、ブラウザで開けない MXF なども開けます。

## 起動

Windows:
- `run.bat` をダブルクリック（初回だけ `.venv` を作って必要なパッケージを入れます）
- 動画ファイルを `run.bat` かウィンドウにドロップしても開けます
- コマンドなら: `.venv\Scripts\python.exe zoom_player.py 動画.mp4`

macOS（Python 3.10 以上が必要。`python3` が使えること）:
- ターミナルでこのフォルダへ移動して `bash run_mac.sh [動画ファイル]`（初回だけ `.venv` を作ります）
- 動画はウィンドウにドロップしても開けます

## Blackmagic SDI 出力（macOS）

DeckLink / UltraStudio（UltraStudio Mini Replay 12G などの再生用の機器も含む）の SDI へ、画面で拡大している範囲を出せます。

準備:
1. Blackmagic Desktop Video（ドライバ）を入れ、システム設定 → 一般 → ログイン項目と機能拡張 → ドライバ機能拡張 で
   Blackmagic のドライバを許可する（Desktop Video Setup で機器が見えれば OK）
2. Blackmagic の「Desktop Video SDK」を入手して展開し、`bash build_sdi_mac.sh <SDK のフォルダ>` で
   `sdi/libzvp_decklink.dylib` を作る（SDK のフォルダを省くと、リポジトリの隣の `Blackmagic DeckLink SDK *` を探す）。
   `build_mac.sh` で .app を作るときも、このライブラリを一緒に入れる

使い方:
- 上の「SDI出力」で出力形式（解像度・fps）を選ぶ。メニューは開くたびに機器を探し直す。「オフ」で止める
- 出すのは画面と同じコマの、拡大している範囲（ミニマップや文字は出さない）。倍率と、画面の真ん中に見えている点を
  合わせるので、画面と出力の縦横比が違うと見える範囲は少し変わる。「ピクセル表示」も同じように効く
- 10bit で出せる形式は 10bit YUV 4:2:2 (v210)、それ以外は 8bit (2vuy)。色は BT.709 の映像範囲で、
  BT.709 の動画なら YUV の値のまま出る（超白なども切らない）
- 機器の出力のコマごとに 1 回、GPU で出力の解像度に描き直して送る。送った絵は機器の予約出力で 3 コマ後
  （59.94p で約 50ms。4K など 1 コマが 8MB を超える形式は 4 コマ後、約 67ms）に出るので、読み出しや送るのが多少遅れても出力のコマの間隔は乱れない。
  一時停止中は最後の絵を出し続ける
- 再生中に、動画の進む速さ（fps × 速度）と出力の fps が整数倍（59.94 と 59.94 / 60、29.97、119.88 など）なら、
  画面に出た新しいコマを順番に予約して出す（29.97 → 59.94 は 1 コマを 2 回、119.88 → 59.94 は 2 コマに 1 コマ）。
  出力の時計で拾い直さないので、画面と出力の時計のずれでコマが重なったり飛んだりしない。
  画面（120.00Hz）は 59.94fps の動画を 60.00 コマ/秒で進めるので、その差を合わせるために 20 秒に 1 回ほど 1 コマ飛ぶ。
  整数倍でないとき（50 → 59.94 など）は、出力のコマごとにそのとき画面に出ているコマを出す
- M1 で 4K 59.94fps（10bit 4:2:2 も）の動画を 2160p で出すと、画面の書き換えを 1 秒に数回取りこぼすが
  （メモリと CPU をほぼ使い切る）、出力には画面に出たコマが順番に並ぶので全コマ出る
- 右上のバッジに「SDI 形式 ・ 送ったコマ ○ / 秒」が出る
- GPU 描画のときだけ使える。Windows には今は対応していない

確認: `.venv/bin/python tools/check_sdi.py` で、GPU が詰めたバイト列が計算どおりか（機器なしで確認）と、
機器がつながっていれば実際に送れたコマ数を確かめます。

## 配布用ビルド

- Windows: `build.bat` で `dist\ZoomVideoPlayer\ZoomVideoPlayer.exe` ができます（PyInstaller、フォルダ形式）。
  配るときは `dist\ZoomVideoPlayer` フォルダごと渡してください（約 165MB、Python のインストール不要）。
- macOS: Mac の上で `bash build_mac.sh` を実行すると `dist/ZoomVideoPlayer.app` ができます
  （PyInstaller はその OS 用のものしか作れないので、Windows では作れません）。
  Finder で動画を右クリック →「このアプリケーションで開く」や、Dock のアイコンへのドロップでも開けます。
  署名していないので、初回は .app を右クリック →「開く」で起動してください。
- 使わない Qt の部品は `ZoomVideoPlayer.spec` の `DROP` で外しています（Windows / macOS 両方の名前を書いています）。

## できること

- 左ドラッグで囲んだ範囲を拡大、ホイール（macOS はトラックパッドのピンチも）でカーソル位置を中心に拡大、
  右ドラッグ / Ctrl+ドラッグ（macOS は ⌘+ドラッグ か control+ドラッグ）で移動
- 拡大中はミニマップ（クリックでその位置へ移動）、「ピクセル表示」で画素をぼかさず表示
- コマ送り（`,` `.`）はフレーム単位で正確。fps はファイルの情報から取得（119.88 と 120 も区別）
- 再生は標準では動画の fps のまま。「再生fps」で値（23.976〜240）を選ぶと、動画の fps ではなく
  その fps で 1 コマずつ強制再生します（例: 59.94fps と記録された 120fps 撮影の MXF を「120 で強制」で
  本来の速さで見る）。コマ番号・シーク・コマ送りは動画の fps のままです。「速度」とも組み合わせられます
- デコードが強制 fps に追いつかないときは、止まらずに、出せる速さで全コマを順に表示します
  （バッジに「デコードが追いつかないため、出せる速さで全コマ表示 (スロー)」と出ます）
- ループ再生（`L`）、A-B 区間ループ（`[` `]`、解除は `\` か `¥`）
- 右上に「描画 ○ / ○ fps」「デコード ○ fps」「画面 ○ Hz」と、追いつかない原因を表示

操作の一覧は画面の「操作方法」ボタンで見られます。音声は再生しません（映像の確認用）。

## テスト

- `run_tests.bat`（macOS は `bash run_tests.sh`、または `run_tests.py` を直接）: 自動テスト。画面は出さずに CPU 描画で、
  シーク・コマ送り・シークバー・再生・ループ・GPU から CPU への切り替えなどを確かめます。
  テスト用の動画は各コマにフレーム番号を描いてあり、表示されたコマの番号を読んで答え合わせします。
- `.venv\Scripts\python.exe tools\check_gpu.py [画面番号]`: 本物の画面で GPU 描画を確かめます
  （色が BT.709 の計算どおりか、コマ送りで GPU が描いた絵が正しいコマか、1080p / 120fps を何コマ出せるか）。
- `.venv\Scripts\python.exe tools\check_realtime.py [画面番号] [--fps 144]`: 再生のリアルタイム性を測ります
  （等速で飛んだコマ数、表示が止まった最長時間、再生開始までの時間、A-B ループの折り返しの止まり）。
- macOS では `.venv/bin/python tools/check_gpu.py`、`.venv/bin/python tools/check_realtime.py` のように実行します。

## 仕組みのメモ

- 表示は GPU (OpenGL) で行います。デコードした YUV をそのままテクスチャにして、
  色変換 (BT.709 / BT.601、映像範囲 / フル範囲) と拡大縮小をシェーダーで行うので、CPU は画素に触りません。
  右上のバッジに「GPU描画」と出ます。
- OpenGL が使えない PC では自動で「CPU描画」に切り替わります（遅くなります）。
  環境変数 `ZVP_RENDERER=cpu` で CPU 描画を強制できます。
- GPU 描画の表示部分はウィジェットではなく専用の OpenGL ウィンドウ (QOpenGLWindow) で、
  メインウィンドウに埋め込んでいます。ウィジェットだと Qt がウィンドウ全体を合成し直す分遅く、
  1080p / 120fps で 120 コマ出せなかったためです。キー入力とドロップはメインウィンドウへ渡しています。
- 絵は裏画面 (OpenGL のバックバッファ) に描き、画面の書き換えに合わせて表と入れ替えます。
  テクスチャも 2 組持ち、再生中は今のコマを描く命令を出したあと、次に出すコマをもう 1 組へ
  先に送っておきます。次の書き換えではテクスチャを送らずに描くだけで済みます (ほぼ全コマで当たります)。
- 表と裏の入れ替えは画面の書き換え (垂直同期) 1 回ごと (swap interval 1) と明示しています。
  グラフィックドライバの設定で同期が切られていると、バッジに「GPU描画 (垂直同期なし)」と出ます。
- GPU 描画では、コマを選ぶのは画面の書き換えの直後だけです。書き換えの知らせは 0〜9 ms ほど
  ばらばらに遅れて届くので、その揺れを除いた時刻 (player_vsync.VsyncTimer) を基準に、次の書き換えの
  時刻に半コマ足した時刻で四捨五入して選びます。
- 動画と画面の速さが同じか整数倍・整数分の 1 (144fps を 144Hz、59.94fps を 60Hz、72fps を 144Hz など) の
  ときは、壁時計ではなく書き換え 1 回につきちょうど決まったコマ数進めます (VsyncLock。バッジに
  「書き換えに合わせて進行」と出ます)。144Hz と表示される画面も実際は 143.97Hz などとわずかにずれていて、
  壁時計で選ぶとコマの切り替わりと書き換えが重なった所でコマ飛びと二度出しが続くためです。
  本当に描画が遅れて書き換えを飛ばしたときだけ、壁時計との差で追いつきます。
- 再生中のデコードは別プロセスで行い、フレームを共有メモリ経由で受け取ります。
  同じプロセスのスレッドだと Python の GIL を画面側と奪い合い、描画が止まるためです。
- 共有メモリのスロットはデコードキャッシュ (先読みの貯め) を兼ねます。256MB まで (1080p の YUV で
  82 コマ = 120fps で約 0.7 秒) 先にデコードしておくので、デコードが一瞬遅れても表示は止まりません。
  右上のバッジに「先読み ○ 秒」と出ます。
- 停止中は、操作が落ち着いて 0.15 秒たったら今の位置から先読みを始めておきます。再生ボタンを押すと
  貯めてあるコマからすぐ (1 コマ以内に) 始まります。
- ループ再生 (全体・A-B 区間) の折り返しはデコード側で行い、B の手前を表示している間に A からのコマを
  貯めておくので、折り返しで止まりません (1 コマ分の間隔で次の周に入ります)。
- 表示時刻に間に合わないコマは、デコード側で変換を省いて捨てます。
- 停止中のシーク・コマ送りは画面側で直接デコードします。停止中は裏のスレッドが、表示している
  コマの手前 48 コマ（キャッシュ 384MB の 2/3 まで。1080p 10bit 4:2:2 なら 30 コマ）を先に
  デコードしておくので、1 コマ戻るのは最初の 1 回からすぐ出ます。続けて戻って残りが 2/3 を
  切ったら、その手前を続けて用意します。キャッシュがいっぱいになったら、表示中のコマから
  遠いものから捨てます（先のコマは順にデコードすればすぐ出せるので、手前のコマを優先して残します）。
- シークバーをドラッグ中は最後の位置だけを近いキーフレームで素早く表示し、離したら正確なコマを出します。
- 壊れたパケットは読み飛ばして続けます。
- 120Hz を超える画面 (144Hz など) にも対応しています。画面の Hz より fps の高い動画 (240fps など) では、
  デコード側が「画面が次の書き換えで選ぶコマ」だけを変換して送り、残りは変換を省きます
  (画面側は書き換えのたびに、次の書き換えで表示する時刻をデコード側へ知らせます)。
  見えるコマ数の上限は画面の Hz です (144Hz なら 144 コマ/秒)。
- GPU 描画の書き換えは、Qt の update() ではなく描画の要求を直接送って行います。update() は Windows では
  5 ms ほど待ってから描くので、144Hz (1 回 6.9 ms) では毎回のように書き換えを取りこぼすためです。
  右上の文字や枠は、中身が変わったときだけ画像に描き直して重ねます (毎コマ描くと 1.5 ms かかるため)。
- デコード用のプロセスの優先度は普通のままにして、画面側のスレッドだけ優先度を上げています。
  デコードを「通常以下」にすると、ほかのアプリ (ブラウザや Claude など) に CPU を取られて先読みが空になり、
  120fps の動画でもコマ落ちしました。逆に画面側を上げないと、240fps のデコードに CPU を取られて
  書き換えを取りこぼします。
- GPU 描画のテクスチャへの転送は、いったん GPU の転送用バッファ (PBO) へ写してから GPU に写させます。
  手元のメモリから直接送ると macOS ではドライバが CPU で写し直し、4K 10bit 4:2:2 で 1 コマ 14 ms かかって
  35 コマ/秒しか出ませんでした。転送用バッファへ写すのも次のコマを先に送るときは裏のスレッドで行うので、
  GUI のスレッドでかかるのは 1 コマ 0.2〜1 ms ほどです (4K 10bit で 60 コマ/秒出ます)。
- GPU 描画では、デコード結果の形式をそのまま受け渡します。8bit / 10bit / 12bit、4:2:0 / 4:2:2 / 4:4:4 の
  YUV に対応し、10bit 4:2:2 (XAVC などの業務用カメラの MXF) も CPU で変換しません
  (以前は 8bit 4:2:0 への変換に 1 コマ 2〜4 ms、4K 10bit では 57 ms かかっていました)。
  それ以外の形式 (NV12 や RGB など) は yuv420p に変換してから渡します。
- ボタンに絵文字 (🔁 ⏸ ⛶ など) を使うと Windows が絵文字フォントを読み込み、起動が 2〜3 秒遅くなるので使っていません。
